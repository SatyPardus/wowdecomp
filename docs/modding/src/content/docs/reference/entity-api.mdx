<Aside type="caution" title="Declared, not implemented">
The generated typings (`wowdecomp.d.lua`) declare these classes: `C3Vector`, `Quat`, `WOWGUID`, `CGObject_C`, `CGUnit_C`, `CGPlayer_C`, and `ClntObjMgr` (with methods such as `GetHealth`, `GetPower`, `GetActivePlayer`, `GetObject`). **No Lua bindings for them exist in these commits.** The globals are not defined at runtime. Calling them fails with a nil-index error.
</Aside>

## What you can use today

| Source | Shape |
| --- | --- |
| Positions in hooks (`OnWorldHitTest`, `OnTerrainTrack`) | `{ x, y, z }` tables |
| `ModCore.GetLastHitPoint()` | Three numbers |
| GUIDs in hook arguments | Lua numbers (lossy above $2^{53}$) |
| `ModCore.GetLastHitGuid()` | Hex string and number |
| `guid` fields in [Net schemas](/reference/net/) | `{ low, high }` |
| Pointer arguments (`objectPtr`, `tooltip`, `worldFrame`, `msg`, `namePlatePtr`, `dataStore`) | Opaque light userdata. Lua cannot read or call through them; treat them as handles |
| `caster` in `OnTooltipEvaluate` | A table with `GetAttackPower()` and `GetSpellPower(school)` |

## Working with existing client APIs

The mod runtime shares the Lua state with the UI, so the standard 3.3.5 Lua API (`UnitHealth`, `GetSpellInfo`, `CastSpellByName`, ...) is available wherever the UI layer allows it. Use the hooks as triggers and the Blizzard API for data.
